# 开发目标与路线图

更新时间：2026-11-01。本文记录项目目标、范围与开发优先级；不把计划能力当成已实现功能。

## 项目定位

Memory Share Kit 是面向个人、多电脑、多 Agent 的长期记忆共享层。

核心使用场景：用户在电脑 A 上通过 Hermes 形成项目决策，之后在电脑 B 上使用 Codex 或 MiniMax Code，能够检索并延续该决策；不必重复介绍整个项目背景。电脑与 Agent 都可以更换，已确认的项目知识应保留且可追溯。

Obsidian 是人类阅读、搜索和整理知识的入口。OneDrive 是普通笔记同步及备份渠道。Noema 只是 iPad/iPhone 离线场景的边缘补充，不决定电脑端共享记忆的架构和上线进度。

## 核心开发目标

| 目标 | 具体要求 | 成功的判断方式 |
|---|---|---|
| 多电脑、多 Agent 共享 | 支持 Windows、macOS、Linux，优先接入 Hermes、Codex、MiniMax Code 的本机运行环境 | 不同电脑上的不同 Agent 能读取同一事实 ID、来源和版本 |
| 保留原生能力 | 不覆盖宿主的原生记忆、会话数据库、配置及已有工具 | 停用共享层后，原有工作流继续可用 |
| 本地优先 | 每台电脑独立保存共享快照、队列和回执 | 服务不可达时仍能本地读取和持久保存新增 |
| 故障恢复 | VPS 恢复后自动补传和增量拉取 | 已落盘事件不会因断网、进程退出或响应丢失而消失 |
| 幂等和去重 | 唯一事件 ID、稳定 scope+key；相同请求重复执行不重复变更 | 重复同步不产生重复事实；不承诺任意语义表达自动正确归并 |
| 并发安全 | 更新携带基础版本；竞争修改保存为冲突 | 两台电脑改同一事实时不会静默覆盖任意一方 |
| 生命周期管理 | 区分候选、已确认、已撤销；保留来源与必要历史 | 旧离线设备不能自动复活已撤销事实 |
| 单一 Vault | 分类清晰，用户笔记与生成视图分工明确 | Obsidian 能正常阅读和搜索，不暴露大量运行状态文件 |
| 低维护 | 复用现有网络、OneDrive 与 rclone；不引入日常 Git 同步 | 安装、启动、重试、备份、排错和回滚有明确路径 |
| 可扩展 | 统一工具协议，新增宿主只增加接入适配 | 无需同步各产品内部数据库即可增加 Agent |

个人共享事实使用 `global`；项目知识使用稳定的 `project:ID`；设备路径等差异使用 `local`，不跨电脑发布。项目身份不能依赖各电脑不同的绝对路径。

## 必须支持的工作流

### 1. 任务开始时检索

Agent 查询本机相关项目记忆和必要的个人偏好，说明过期、候选或待同步状态。检索内容是资料，不是执行授权。当前代码和用户最新说明与旧记忆冲突时，应核实来源。

### 2. 稳定知识沉淀

项目约束、架构决策、已验证解决办法、用户明确要求保留的偏好，可保存为原子事实。保留来源和确认状态，不把完整聊天、临时推理、凭据和大量日志全部塞入记忆。

### 3. 故障期间继续使用

VPS 不可用时，其他电脑使用最后同步快照及本机新增；跨电脑最新信息交换可以暂停。恢复连接后补传。运行在故障 VPS 上的 Hermes 本身不能继续运行，记忆层也不能替代不可用的云模型服务。

### 4. 人工阅读与整理

共享事实导出为 Obsidian Markdown。用户在普通笔记目录补充资料，通过 Agent 提交选定内容。第一版不把任意直接修改生成文件视为已提交主库，也不让多个同步器管理同一个目录。

### 5. 移动端离线补充

Noema 使用预先导入、完成索引的记忆资料包及选定 Obsidian 文档进行离线检索、总结、推理。实际执行动作以已验证的模型、工具和权限为限。优先减少准备与更新步骤，但不承诺持续关联 Vault、自动刷新索引或离线记忆自动回流。

## 自动化的准确含义

- 记忆已经提交到本机队列后，存储、同步、重试和补传应自动执行。
- 在宿主支持范围内，通过项目规则和可验证的 hooks 改善任务开始检索与结束保存。
- MCP 已配置不等于模型每轮一定调用，更不等于所有对话已经自动捕获。
- 用户不应日常处理 Git、手工复制数据库或大量冲突文件。
- 真正相互矛盾的事实仍允许用户集中确认，不能为追求“无感”而错误合并。

## 分阶段路线

### 阶段一：打通真实使用与恢复

最高优先级：完成 Windows、macOS、Linux 实机安装与原生自启动验证；打通至少两台电脑、两个不同 Agent 的实际工具调用；完成协调服务停机、客户端退出、恢复补传及并发修改验收。

同时验证一个 Vault 的 OneDrive 配置、生成目录排除、真实远端备份上传与恢复。先跑通可靠闭环，再扩展功能。

### 阶段二：降低日常维护成本

根据实机问题完善状态与诊断、版本升级和数据库迁移流程、凭据轮换、失败重试策略、日志与备份保留策略。

事件和回执压缩必须先定义恢复边界，不能在未证明可恢复前自动删除历史。保持宿主原生配置可回滚。

### 阶段三：改善记忆使用效果

评估中文全文索引、项目摘要和上下文预算管理；必要时再增加向量检索。

摘要应保留来源事实及版本，随来源更新或撤销而失效重建，不能替代原始事实。自动抽取的内容默认候选，不由模型自行提升为已确认事实。

逐个宿主验证官方 hooks 或 Hermes MemoryProvider，提升自动检索和知识沉淀的一致性，防止 MCP、原生镜像和自动抽取之间循环写入。

### 阶段四：按需改善人机入口

如果用户经常需要在 Obsidian 内新增、更新、撤销事实和处理冲突，再做小型插件；不重造笔记同步器，不将 iOS 插件作为常驻 MCP 服务。

Noema 优先完成资料包导入、旧资料替换、离线检索和可用工具验证；只有官方接口足以支持时才增加更自动的关联流程，不开发新的移动 App。

阶段没有预先承诺日期；是否完成以验收记录为准。

## 验收底线

- [ ] Windows/macOS/Linux 本机安装、自启动、停止与回滚经过实机测试。
- [ ] 不同电脑、不同 Agent 能读取同一事实 ID 和版本，保留各自原生记忆。
- [ ] 协调端不可用时，本地查询和新增可用；客户端退出重启后新增仍在。
- [ ] 服务端提交后丢失响应，重复同步不产生重复事实。
- [ ] 并发更新不会静默覆盖；冲突内容能核对并显式解决。
- [ ] 更新与撤销竞争、旧设备重连不会错误复活事实。
- [ ] 实际 OneDrive 同步和备份失败后能恢复；备份经过实际恢复演练。
- [ ] Obsidian 能阅读、搜索共享知识，不要求日常手工处理 Git。
- [ ] Noema 在飞行模式下能检索已导入资料，明确资料日期及工具边界。
- [ ] 文档、安装文件和实际能力一致，未完成的项目保持清楚标注。

这是一份系统级待验收清单，包含已被 Linux 自动化测试覆盖的子项，不代表这些子项尚未实现；跨平台和真实环境验证仍需单独记录。

## 范围边界

当前不做：新的移动 App、双主自动切换、跨设备点对点数据库复制、多人权限系统、任意自然语言冲突自动裁决、同步宿主运行数据库、自动抓取所有聊天或自动授权执行记忆中的命令。

已有局域网或虚拟局域网安排直接复用，不另行设计网络。项目不强制购买 Obsidian Sync、Working Copy 或其他付费同步服务；现有电脑、VPS、存储和宿主模型服务的成本不由此项目消除。

核心取舍：优先保证事实可追溯、离线数据可保存、恢复过程可验证；增加组件必须解决真实问题，不能仅为架构复杂而增加。
